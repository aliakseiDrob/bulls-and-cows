# Архитектурный дизайн проекта «Быки и Коровы»

В данном документе описаны ключевые архитектурные решения, структуры данных, оценка вычислительной сложности алгоритмов и применение принципов чистого кода (Clean Code) в рамках реализации задания.

---

## 1. Структуры данных и алгоритмы

### Структура состояния (State) и история попыток

Для управления состоянием приложения была выбрана модель **Plain Old JavaScript Object (POJO)** с применением модификаторов `readonly` на уровне TypeScript (`State`, `Settings`, `HistoryEntry`).

- **Массив объектов для истории (`readonly HistoryEntry[]`)**: История попыток хранится в виде плоского неизменяемого массива. Выбор обусловлен необходимостью последовательного добавления элементов в конец истории без изменения порядка и декларативного рендеринга таблицы UI (`.forEach`). Применение иммутабельного оператора spread (`[...state.history, entry]`) гарантирует отсутствие сайд-эффектов мутации.
- **Иммутабельность как стержень**: Логика игры построена по принципам чистой архитектуры состояний (по аналогии с Redux/Flux architecture). Изменение любого параметра (например, переключение флага `showLeaderboard` или отправка попытки) возвращает ссылку на абсолютно новый снимок (snapshot) объекта состояния. Это полностью исключает утечки и делает структуру предсказуемой.

### Описание алгоритма `evaluateGuess`

Алгоритм вычисляет совпадения между секретной строкой `secret` и попыткой `guess` без применения императивных счетчиков и циклов:

1.  Обе строки переводятся в нижний регистр и деструктурируются в массивы символов (`.split('')`).
2.  **Быки (Bulls)**: Массив `guessChars` фильтруется (`.filter`) по условию строгого равенства символа и его индекса с массивом `secretChars`. Длина отфильтрованного массива — количество быков.
3.  **Коровы (Cows)**: Массив `guessChars` фильтруется по условию: символ присутствует в секрете (`secretChars.includes(char)`), но его индекс в попытке не равен индексу в секрете. Длина массива — количество коров.

### Описание алгоритма `countPossibleSecrets`

Алгоритм вычисляет количество возможных размещений элементов без повторений (математические перестановки $P(n, k)$) для заданной длины числа $k$ (`length`) и размера алфавита $n$ (`base`):

1.  **Чистая хвостовая рекурсия**: Функция вычисляет значение по формуле $P(n, k) = n \cdot P(n - 1, k - 1)$. Базовый случай рекурсии — достижение длины 0, возвращающий 1.
2.  **Мемоизация через замыкание**: Функция высшего порядка оборачивает рекурсивный вычислитель, создавая изолированную структуру `Map` для кэша. Перед каждым вычислением генерируется уникальный ключ `${length}-${base}`. Если значение уже рассчитывалось ранее, оно мгновенно возвращается из памяти без повторного спуска по стеку вызовов.

## 2. Вычислительная сложность (Big O Notation)

Пусть $L$ — длина секретного числа (`length`), а $B$ — основание системы счисления (`base`). На практике по условиям ТЗ $L \le 6$, а $B \le 16$, то есть величины ограничены константами. Однако с теоретической точки зрения обобщенная сложность выглядит следующим образом:

### 1. `isValidGuess` — Сложнсть: $O(L)$

- **Обоснование**:
  - Преобразование строки в массив и создание `new Set(chars)` для проверки уникальности занимает время, пропорциональное длине строки, то есть $O(L)$.
  - Итерация `.every` запускает валидатор символов для каждого элемента. Проверка одного символа в `createDigitValidator` через метод `.includes` на строке длиной до $B$ занимает $O(B)$ времени.
  - Итоговая сложность: $O(L \cdot B)$. Учитывая, что $B$ константно ограничено числом 16, общая сложность редуцируется к линейной $O(L)$.

### 2. `generateSecret` — Сложность: $O(L \cdot B)$

- **Обоснование**:
  - Функция использует безопасную хвостовую рекурсию, совершая строго $L$ шагов до тех пор, пока глубина аккумулятора не станет равной требуемой длине.
  - На каждом шаге рекурсии массив доступных элементов фильтруется (`.filter`), чтобы исключить уже выбранный символ, что занимает $O(B)$ операций.
  - Итоговая сложность: $O(L \cdot B)$. Поскольку на практике $B \le 16$, алгоритм гарантированно отрабатывает за стабильные $O(L)$ шагов без возможности ухода в бесконечный цикл.

### 3. `evaluateGuess` — Сложность: $O(L^2)$

- **Обоснование**:
  - Подсчет «быков» использует метод `.filter` длиной $L$, внутри которого происходит прямое O(1) сравнение символов по индексу. Это занимает $O(L)$ времени.
  - Подсчет «коров» использует `.filter` длиной $L$, внутри которого для каждого символа вызывается метод `secretChars.includes(char)`. Поиск подстроки/символа в массиве длиной $L$ в худшем случае занимает $O(L)$ операций.
  - Итоговая сложность: $O(L) + O(L \cdot L) = O(L^2)$. На максимальной длине $L=6$ алгоритм выполняет не более 36 базовых операций, что обеспечивает мгновенный отклик.

### 4. `countPossibleSecrets` — Сложность: $O(L)$ (без кэша) / $O(1)$ (с кэшем)

- **Обоснование**:
  - При первом вызове для уникальных параметров алгоритм совершает рекурсивный спуск на глубину, равную $L$, производя по одной операции умножения на каждом уровне. Сложность составляет $O(L)$.
  - При всех последующих вызовах с теми же аргументами чтение из структуры `Map` (хэш-таблицы) по ключу строки выполняется за константное время $O(1)$.

## 3. Принципы чистого кода (Clean Code)

В проекте применены фундаментальные принципы написания чистого, читаемого и тестируемого кода:

### 1. Единая ответственность (Single Responsibility Principle)

Каждая функция и модуль выполняют ровно одну задачу.

- _Пример_: Модуль `src/scoreService.ts` инкапсулирует в себе исключительно механизмы взаимодействия с `localStorage`, фильтрацию и сортировку рекордов. Он не знает о существовании DOM и не занимается рендерингом.
- _Пример_: Функция `createDigitValidator` в файле `src/createDigitalValidator.ts` создаёт специализированный валидатор для одного конкретного символа и не занимается валидацией всей строки.

### 2. Принцип DRY (Don't Repeat Yourself) и параметризация тестов

Устранено дублирование кода как в логике, так и в тестовых сценариях.

- _Пример_: В файлах `src/gameState.test.ts`, `src/isValidGuess.test.ts` и `src/countPossibleSecrets.test.ts` вместо написания десятков однотипных блоков `it(...)` используется декларативный табличный метод раннера Vitest — `it.each([...])`. Это позволило сократить объем тестовых файлов в 3 раза, сделав их легко расширяемыми.

### 3. Декларативность вместо Императивности (Functional Programming)

Полный отказ от низкоуровневых управляющих конструкций `for`, `while`, `let` счетчиков и промежуточных мутаций данных внутри бизнес-логики.

- _Пример_: В функциях `evaluateGuess` (вычисление результатов) и `isValidGuess` (валидация строки) циклы заменены на встроенные декларативные методы высшего порядка: `.every()`, `.some()`, `.filter()`.
- _Пример_: В функции `generateSecret` итеративный цикл заменен на чистую хвостовую рекурсию с передачей иммутабельного пула доступных символов.

### 4. Принцип наименьшего удивления (Principle of Least Astonishment) и строгая типизация

Архитектура проекта предсказуема благодаря прозрачному именованию сущностей и иммутабельным контрактам типов данных.

- _Пример_: В файле `src/state.ts` все интерфейсы (`State`, `Settings`) объявлены через конструкцию `readonly`. Это защищает разработчика от случайных неявных изменений (сайд-эффектов), подсвечивая любые мутации ссылок еще на этапе компиляции TypeScript.
- _Пример_: Имена функций используют понятные глаголы действия: `createInitialState`, `startRound`, `applyGuess`, `toggleLeaderboard`, четко отражая их назначение.

### 5. Безопасность DOM-манипуляций (Защита от XSS)

- _Пример_: В модулях интерфейса `src/ui/gameView.ts`, `src/ui/settingsView.ts` и `src/ui/leaderboardView.ts` полностью отсутствует свойство `innerHTML`. Все элементы создаются исключительно через `document.createElement`, а текстовые ноды наполняются через безопасное свойство `textContent`. Очистка контейнеров перед ререндером производится через производительный и безопасный метод `.replaceChildren()`, предотвращая утечки памяти и атаки типа скрипт-инъекций.
